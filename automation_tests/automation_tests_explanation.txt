### 3. How the Tests Are Executed
1. **Setup** – The test runner reads environment variables:
   - `TEST_API_URL` (primary API endpoint)
   - `TEST_BASE_URL` (UI base URL)
   - `SECURITY_AUTHORIZED=true` (required flag to document permission)
   - Optional toggles (`SECURITY_ENABLE_RATE_LIMIT_TESTS`, `SECURITY_ENABLE_MUTATION_TESTS`, etc.) that enable or skip expensive checks.
2. **Mocha / Jest** – All `*.spec.js` files are loaded by Mocha (via `npm test`). Each file contains a series of `describe` / `it` blocks that issue HTTP requests (using `axios`) or Selenium commands (`driver_helper`).
3. **Payload Generation** – Helper `security_payloads.js` defines payload dictionaries for:
   - **Sort / order** values (including unknown columns such as `not_a_real_column`).
   - **SQL/NoSQL injection strings**, **XML‑entity payloads**, **XSS vectors**.
   - **JWT manipulation** (unsigned, expired, tampered). The payloads are mixed with legitimate data to test validation layers.
4. **Reporting** – After the run, `scripts/generate_security_report.js` calls the two helper functions `writeEndpointInventoryReport` and `writeChecklistReport` which produce:
   - **Endpoint inventory** (Markdown table of discovered routes). 
   - **Checklist coverage** (summary of which security categories were exercised and how many tests passed). The paths are printed to the console (see lines 9‑10 of the script). 
5. **Mochawesome HTML** – The HTML report lists each spec, the duration, and a pass/fail badge per test case. The snippet you shared is a trimmed view of that report.

### 4. Why These Payloads & Scenarios?
| Category | Reason for testing |
|----------|--------------------|
| **Authentication boundaries** | Verify that only authorized credentials can obtain tokens or privileged endpoints. Prevents default/weak passwords and token forgery. |
| **Query payload handling** | Many APIs accept `sort`, `order`, `filter` parameters. Passing unknown or malformed columns can lead to SQL errors or data leakage (the *unknown sort* bug discovered). |
| **Response exposure** | Checks that internal error messages, stack traces, or secrets are not returned to the client. |
| **High‑risk public endpoints** | Publicly reachable endpoints (health, version, telemetry) often expose version numbers or configuration that attackers can fingerprint. |
| **JWT security** | JWTs are a common auth mechanism; testing for `alg:none`, missing Bearer, expiration, and tampering ensures the server validates signatures correctly. |
| **Authorization / BOLA** | Object‑level access control (BOLA – Broken Object Level Authorization) can let a low‑privileged user access another user’s data. Tests with known cross‑resource IDs (`TEST_BOLA_OTHER_RESOURCE`) expose such bugs. |
| **Scope discovery** | An attacker first maps the API surface; the discovery test ensures the suite knows every reachable route and its expected methods. |
| **GraphQL & business logic** | GraphQL introspection can reveal the full schema. Business‑logic checks (e.g., negative quantities) ensure the server enforces domain rules beyond simple validation. |
| **Input validation & parameter manipulation** | Classic injection vectors (SQL, NoSQL, XML‑XXE, XSS) test server‑side sanitisation and request parsing. |
| **Logging & monitoring** | Even if the server blocks a request, it should emit audit entries for forensic analysis. |
| **Misconfiguration & data exposure** | Validates security headers (`Content‑Security‑Policy`, `X‑Frame‑Options`), proper CORS configuration, and that debug endpoints are disabled in production. |
| **UI security** | Client‑side attacks (XSS, CSRF, rate‑limit bursts) are exercised through Selenium to emulate a real user/browser. |

### 5. Why the “unknown sort” Error Appears
- **Symptom:** Several endpoints return HTTP 500 when the `sort` query parameter is set to a column that does not exist (e.g., `?sort=not_a_real_column`).
- **Root cause (documented in `SECURITY_TESTING.md` lines 71‑81):** The backend currently validates `sort` using a *regex‑only* whitelist which allows any alphabetic token. When the token does not map to a real column, the database throws an internal error, bubbling up as a 500.
- **Remediation (line 81):** Replace the regex check with an **explicit per‑endpoint allowlist** of sortable columns and fall back to a safe default (e.g., `id`). This prevents the server from leaking internal errors and avoids denial‑of‑service via crafted sort parameters.
